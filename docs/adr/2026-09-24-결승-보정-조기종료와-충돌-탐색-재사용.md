# 결승 보정 조기 종료와 충돌 탐색 재사용

- 상태: 적용
- 날짜: 2026-09-24
- 연결 요구사항: REQ-MARBLE-002, REQ-MARBLE-004
- 연결 화면: [SCR-WEB-004](../design/screens/SCR-WEB-004.md)

## 문제

[연결 접촉 보정](2026-09-23-결승-연결-접촉과-보간-겹침-해소.md)으로 겹침은 줄었지만1000개 결승 경기의 계산 비용이 늘었다. 구슬 쌍을 보정하는 도중의 최대 오차로 종료를 판단해, 벽까지 보정한 최종 상태가 이미 분리됐어도 계산을 반복했다. 기본 구슬 분리와 결승 보정에서 같은 벽을 거듭 탐색하는 비용도 컸다.

## 결정

- 결승의 연결된 접촉은 매1/120경기초마다 검사한다. 검사 간격을 다시 늘리지 않는다. 미도착 구슬이64개를 넘으면 벽까지 보정한 뒤 실제 남은 겹침을 확인해0.5 이하에서 종료한다.64개 이하는 기존 보정 중 오차0.15 기준을 유지한다. 최대512회와 실제·표시 겹침1 이하 검사 기준은 유지한다.
- 200개 이상 경기의 결승 구슬 쌍은 기본 충돌에서 반발 속도를 처리하고 단계 끝의 연결 접촉 처리에서 위치를 보정한다. 위치를 바꾸지 않은 기본 접촉에서 벽을 다시 찾지 않는다. 결승 밖 접촉과 작은 경기의 기존 처리는 유지한다.
- 200개 이상 경기에서 결승 진입 구슬이 있으면 내부 이동 분할의 상한을4에서8로 바꾼다. 반지름13보다 작으며 빠른 구슬은 계속 더 나눠 계산한다. 기본 물리 간격1/120초·속도 한도·반발계수0.8·스킬 규칙은 유지한다. 큰 경기의 결승 진입 이후 궤적은 달라질 수 있다.0.25·1·2배속의 같은 경기 시각 결과는 동일해야 한다.
- 구슬마다 주변 격자 범위와 블록 후보 목록을 재사용한다. 구슬의 범위나 경기 탐색 자료가 바뀌면 다시 찾는다. 블록의 생존 여부는 접촉 때마다 확인한다. 결승 외 블록의 최대 이동 범위보다 아래에서는 결승 블록만 찾는다.
- 벽의 각도·크기·둥근 모서리 계산값을 재사용한다. 회전이나 크기 변화는 즉시 반영한다. 구슬 충돌의 격자는 숫자 키를 쓰며 후보의 기존 번호 순서를 유지한다.
- Worker의 요청당 계산 예산을6ms에서12ms로 늘린다. 최대4물리 단계와 상세 상태 최대60회/초는 유지한다. 남은 시간과 이벤트를 버리지 않는다. 화면 상태를 받은 뒤 화면 변경 작업이 시작되기 전에 다음 계산을 요청한다. 정지 시 최신 상태를 확보하고 초기화한 경기의 늦은 응답을 무시한다. 단일 단계가12ms보다 길 수 있으므로 응답 시간의 절대 상한은 아니다.
- 벽 이동 경로 검사·중앙 입구 진입 기록·최종 위치의 골인 판정·번개 구슬 밀림·얼음 고정·보간 좌표 보정은 유지한다. 화면 보정으로 실제 경기 상태를 바꾸지 않는다.

## 검증 방법

1000개 실제 경기의105경기초 상태를 저장하고 같은 상태에서5경기초를 계산해 변경 전후 비용을 비교한다. 일반 블록을 제거하거나 구슬을 고정하지 않은 상태다. 이 계산 비용과 브라우저의 실제 진행 속도를 따로 기록한다.

1000개 밀집의 실제·표시 겹침, 회전각4가지의35경기초 벽 통과,60개 완주,32개 접전, 배속별 재현성을 확인한다. 재사용 중 블록 회전·크기·생존 여부와 격자·경기 교체를 검사한다. 큰 경기의 결승 계산 중 위로650/초·아래로900/초로 움직이는 구슬이 얇은 장애물에 막히는지도 검사한다.

## 검증 결과

- 관련 단위 테스트93개와 최종 build의 Playwright9개를 통과했다. 정적 검사에 오류·경고가 없었고 변경 코드의 lint·포맷, 요구사항2개, 전체 화면 연결, 정적 build 검사도 통과했다. build는1회 실행했다. 전체 lint와 다른 도구의 전체 테스트는 실행하지 않았다.
- 1000개·스킬ON 밀집 시험에서 실제 겹침은 최대약0.646, 보간 겹침은 최대약0.500이었다. 회전각4가지의35경기초 벽 통과 방지 검사를 통과했다.60개 밀집은48.8~55.4경기초에 모두 도착했고32개 접전은16번 역전하며 최대12.475경기초에 완주했다.
- 실제1000개 경기의 동일한105경기초 저장 상태에서5경기초를 계산했다. 평균 물리 단계 비용은10.68ms에서5.45ms로약49% 감소했다. 느린 쪽5%의 경계는18.76ms에서9.76ms로 감소했다. 전체 계산 시간은6.41초에서3.27초로 줄었다. 큰 경기의 내부 이동 분할 변경으로 최종 위치·도착 수는 달라질 수 있다.
- 개발 화면의 실제1000개·난수47·마지막 방식·스킬/소리ON·2배속에서105.0경기초부터118.9경기초까지 실제10초 측정은약1.39배속이었다.201.7경기초부터221.7경기초까지의 별도 구간은약2.01배속이었다. 그 구간의 Worker 요청당 평균 계산은약12.95ms, 다음 요청 대기는약0.60ms였다. 전달 대기보다 물리 계산이 주요 병목으로 남았다.
- 최종 build의1440×1000 브라우저에서 같은1000개 설정을 다시 측정했다. 출발은약2.00배속, 결승105.0~119.1경기초의10초 구간은약1.41배속이었다. 결승에358개가 있었고 상태 수신은39.6회/초, Canvas 배경 그리기는120회/초였다. 직전 구현의 같은 설정·결승105경기초 시작 측정약0.66배속보다 개선됐지만 심한 밀집에서2배속을 유지하는 기준은 아직 충족하지 못했다. 화면 갱신 횟수만으로 실제 경기 속도가 개선됐다고 판단하지 않는다.
- 실제174.5경기초 장면에서 결승에358개가 있었고 최대 구슬 겹침은약0.500이었다. 일시정지 클릭부터 정지 패널 확인까지29ms였다. 접근성 snapshot 뒤1440px·390px 화면을 확인했으며 가로 넘침이 없었다. 모바일 크기는 데스크톱 브라우저의 화면 크기 시험이며 실제 휴대폰 성능 측정은 아니다.
