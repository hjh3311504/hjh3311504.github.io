# 모바일 출발 지연을 줄이는 계산 요청 상한

- 날짜:2026-09-26
- 상태: 채택
- 요청: 모바일1000개·2배속 경기의 출발 지연 해결

## 원인

[모바일2배속 실측](2026-09-26-모바일1000개-2배속-실측.md)에서 출발5초의 실제 진행은1.55~~1.71배속이었다. 화면은47~~49fps였으며 다음5초에서 밀린 계산을 따라잡았다.

Worker는 요청당12ms 예산 또는4물리 단계에 도달하면 응답했다. 기본 물리 간격은1/120경기초다. 2배속에서4단계는 실제16.67ms에 해당한다. 화면 작업 때문에 요청 왕복이 이보다 길어지면 계산 여유가 있어도 다음 요청을 기다리면서 시간이 밀린다.

추가 계측에서 출발5초 동안247번 요청했다. 요청당 계산은 평균5.59ms였지만 왕복은19.64ms였다. 실제 진행은1.641배속, 남은 계산 시간은1.124초였다. 요청마다4단계를 처리한 결과와 일치한다. 이 계측에는 Worker 시간 기록과 브라우저 CPU 프로파일러를 사용했으므로 아래 최종 성능 표본과 구분한다.

## 결정

- 요청당 최대 단계를4개에서8개로 늘린다.
- 12ms 계산 예산에 도달하면 단계 상한 전이라도 응답한다. 개별 물리 단계는 중단하지 않으므로 한 단계 비용만큼 예산을 넘을 수 있다.
- 계산 요청에 담긴 시간만 처리한다. 미래 시간을 미리 계산하거나 남은 시간을 버리지 않는다.
- 1/120경기초 간격, 충돌·겹침 보정, 지형, 회전바, 스킬·반발 규칙은 유지한다.
- 필수 결승0.25배속과 단계마다 수행하는 연출 판단을 유지한다.
- 상태 전달60회/초 묶음과 이벤트 보존, 정지 시 최신 상태 가져오기를 유지한다.

2배속의8단계는 실제33.33ms에 해당한다. 화면 응답이 잠시 늦어져도12ms 예산 안에서 추가 단계를 처리할 여유가 생긴다.

## 실험과 최종 측정

기존 build의 Worker 응답 코드를 브라우저 요청 가로채기로 바꾼 진단 실험에서 출발2.026배속, 이후2.004배속을 확인했다. 생성 파일을 수정하지 않았다. 이 실험을 확인한 뒤 소스에 적용하고 최종 build를1회 만들었다.

최종 측정은 요청 가로채기와 CPU 프로파일러 없이 실제 build의 Worker로 수행했다. 앞선 미커밋 렌더링 개선은 수정 전후 모두 동일하게 포함했다.

조건은390×844, Chromium headless shell, CPU4배 감속, reducedMotion reduce, 도각도각 키보드,1000개, 난수47, 첫 번째 당첨 방식, 스킬ON·소리OFF·선택2배속이다. 출발5초와 이어지는5초를 연속 측정했다. 준비·시작 후 배속 버튼을2배속으로 바꾼 시점부터 측정하며 시작 준비 대기 시간은 포함하지 않는다.

실제 배속은 Worker 경기 시간 증가량을 실제 경과 시간으로 나눈 값이다. fps는 Canvas 그리기 횟수로 따로 측정했다.

출발 실제 배속의3회 평균은 수정 전1.631배에서2.008배로 약23% 개선됐다. 모든 표본에서 필수 결승 감속은 발동하지 않았다. 측정 구간 끝의 상태 수신 시점 차이 때문에 정확히2.000배로 고정되지는 않는다.

## 검증

- Worker·상태 전달·이벤트 관련 단위 테스트9개 통과.
- 계산 예산이 먼저 소진되는 경우와8단계 상한이 먼저 도달하는 경우를 확인했다. 요청 시간이 짧으면 필요한 단계만 계산한다.
- 0.25·1·2배속에서 직접 물리 계산과 Worker 결과가 같다.
- 8단계씩100번 묶어도 구슬 상태·스킬·충돌 이벤트가 직접 계산과 정확히 같다. 최신 상태를 다시 요청해도 이벤트를 중복 전달하지 않는다.
- 모바일2배속 성능 검사3회 통과. 각5초 표본의 실제 배속1.9~2.1배, 남은 시간0.1초 이하, 화면30fps 이상, 정지 응답200ms 이하를 함께 검사한다.
- 추가 브라우저 검사8개 통과. 모바일·데스크톱1배속, 데스크톱2배속, 화면10fps에서의 계산 유지, 정지·재개·초기화, 번개·바람 발동을 확인했다. 데스크톱2배속은 출발2.004배·59.97fps, 이후2.000배·59.99fps였다.
- 물리·보간 회귀 검사26개 통과.1000개 밀집의 실제 최대 겹침은0.49999 미만, 표시 최대 겹침은0.49947 미만이었다.4단계와8단계 수신 간격 모두에서 표시 겹침1 이하와 실제 상태 보존을 확인했다. 밀집 검사는 일반 블록을 제외한 결승 배치로 진행했다.
- 1000개·회전각4가지·35경기초의 벽 통과 방지와 중앙 통로 진입 검사를 통과했다. 번개 정지 중 밀림의 표시 보간, 얼음 고정과 접촉음 중복 방지도 통과했다.
- 접근성 snapshot을 먼저 확인한 뒤390px·1440px 화면을 확인했다. 가로 넘침이 없고2배속·일시정지·재개 조작부가 표시됐다. 화면 기록은 `output/playwright/startup-390.png`, `startup-1440.png`다.
- build1회, 정적 결과 검증, Svelte 정적 검사 오류·경고0개, 이번 변경 파일의 ESLint·Prettier와 `git diff --check`를 통과했다. 전체 lint·전체 단위 테스트·전체 브라우저 검사는 반복하지 않았다.

## 한계와 재현 자료

이번 변경은 출발 구간의 계산 요청 대기를 줄인다. CPU 계산 자체가12ms 예산을 소진하는 심한 결승 밀집까지 해결했다는 뜻은 아니다. 실제 휴대폰과 GitHub 검사 환경은 별도 확인이 필요하다. 화면 fps를 높이는 것으로 실제 배속 개선을 대신하지 않는다.

- 최종 반복 측정: `npm run test:e2e:built -- tests/team-maker-e2e/marble-performance.spec.js --grep '모바일.*2배속' --repeat-each=3 --workers=1`
