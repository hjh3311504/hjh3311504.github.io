# 파동·결승 접촉·전체 미리보기 개선

- 상태: 결정
- 사용자 설계·구현 승인:2026-09-22 파동·결승 충돌·순위 화면 개선 계획 구현 요청
- 연결: REQ-MARBLE-001·002·003·004, SCR-WEB-004

## 배경

파동이 좁고 오른쪽 결승 경사면은 직선이었다. 회전바가 밀어 올린 구슬과 위쪽 구슬이 겹쳤다. 기존60개 밀집 재현의 회전 각도4가지에서 최대 겹침은11.70~12.31이었다. 구슬 반지름은13이다. 구슬 분리량을4로 제한한 한 번의 처리 뒤 벽 보정으로 다시 생긴 겹침을 풀지 못했다.

준비 화면은60개만 생성했다. 순위 카드에는 번호가 없는 색 점과 별도 번호 줄을 표시했다. 이전의2·4·6열보다 새 구슬·진행률의 한 줄 배치를 우선하기로 사용자가 선택했다.

## 결정

파동 반경은120에서180으로 늘린다. 중심 힘780·거리별 감쇠·0.45경기초 효과·발동 확률·대기 시간은 유지한다. 그림·피격·음향 화면 범위에 같은 반경을 사용하고 도감 배율도 반경에서 계산한다.

오른쪽 벽은 왼쪽 원호를x=360 기준으로 반사한다. 통로 쪽 반지름은407.9024, 중심은 왼쪽(-67.9024, 결승 시작+400)·오른쪽(787.9024, 결승 시작+400)이다. 원호 중심선 반지름은401.9024이고 두께는12다. 양의 회전 범위를 써서 충돌·Canvas·미니맵이 같은 모양을 사용한다. 폭40 출구와 회전바의 길이320·위치·회전 속도는 유지한다.

결승의 접촉 구슬과 연결된 이웃은 아래쪽부터 위치만 반복 보정한다. 접촉 속도 계산은 기존 물리 처리에서 수행한다. 추가 보정에서 반발력·효과음·스킬을 호출하지 않는다. 최대32회 반복하고 검사한 겹침이0.25 이하이면 종료한다. 고정 구슬은 움직이지 않고 도착 구슬은 제외한다. 보정 후 결승을 판정한다. 새 보정의 불필요한 검색을 줄이기 위해 결승 장치5개와 원호의 접촉 가능한 띠를 먼저 확인한다.

순위 카드는1·2·3열, 높이104px·행 간격116px다. 첫 줄의 등수 옆에36px 번호 구슬을 표시하고 진행률 또는 도착 상태는 오른쪽 끝에 둔다. 이름은 다음 줄에서 최대2줄 표시한다. 별도 번호 줄을 제거하되 접근성 설명의 고유 번호는 유지한다. 경기장과 순위 카드는 같은 구슬 그리기 함수를 사용한다.

미리보기는 별도 Worker의 `prepare` 요청에 `preview: true`를 지정한다. 전체 구슬을 나누어 생성하며 경기용 접촉 Map·Set은 만들지 않는다. 최초 응답에도 `preview`를 전달한다. 준비가 끝난 Worker는 종료한다. 명단·맵 변경, 자리섞기, 경기 시작, 화면 종료는 이전 미리보기 작업을 취소한다. 이전 응답은 요청 번호로 거른다. 새 미리보기가 도착하기 전에 이전 경기의 당첨 목록을 다시 채우지 않는다. 공개 API와 저장 설정 형식은 유지한다.

준비 화면은 현재 배율로 표시하며 화면 이동·미니맵으로 전체 구슬을 확인한다. 일부만 표시한다는 안내를 없애고 시작 버튼과 현재 안내를 “레이스 시작”으로 맞춘다.

## 성능 분석 범위

사용자는 현재 로컬 화면이 느리다고 답했다. 이번에는 원인 분석과 개선안 제시까지 요청했다. 물리 엔진 교체·그리기 해상도 축소·추가 일반 최적화는 적용하지 않는다.

측정은1000개·난수47·기본 키보드 맵·마지막 방식·1280×720·화면 해상도 배율1의 Chromium에서 한다. 준비·출발 외에 밀집과 결승은 같은20열·행 간격30의 고정 초기 배치로 구간을 분리한다. 이는 전체 자연 경기의 평균 성능이나 실제 휴대폰 측정이 아니다. 화면 그리기·Worker 응답·표시 시각 정체·실제 경기 시간 진행을 따로 기록한다. 소리와 스킬은 함께OFF/ON 두 조건을 비교한다. 따라서 두 기능 각각의 비용을 단독으로 단정하지 않는다.

비교 사이트는 공개 소스에서 `box2d-wasm`을 사용하며 물리 계산을10ms마다 요청한다. 현재 기본 맵의 장치는46개다.1280×720 화면에서 장면을640×360으로 그린 후 확대하는 것을 실제 화면에서도 확인했다. 우리 기본 맵은1000개에서 장치5596개이고1/120초 고정 계산을 내부에서 다시 나눈다. 두 사이트의 맵·스킬·음향·구슬 그림은 달라 동일 게임의 엔진 성능 비교로 해석할 수 없다.

화면 갱신 간격의95% 값은 약9.8~10.2ms, 가장 긴 간격은13.5ms였다. 하지만 결승 밀집에서는 약80%의 프레임이 이전 표시 시각을 반복했다. 보간은 새 상태가 없으면 미래 위치를 추측하지 않는다. 따라서 Canvas가120fps로 다시 그려져도 구슬의 실제 움직임은 멈춰 보인다.5.05초처럼 측정 창보다 조금 긴 경기 시간은 Worker 묶음 응답의 경계 차이다.

별도의 build 화면 검사에서는 자연 출발과 이어지는 구간을 각각5초 측정했다.1440×1000 데스크톱은119.4~~120.2fps, 일시정지 버튼 반응은2.9ms였다.390×844와 CPU4배 감속 조건은39.0~~51.0fps, 버튼 반응은12.2ms였다. 각5초 동안 경기 시간도 약5초 진행했다. 이 조건은 모바일 크기를 흉내 낸 데스크톱 Chromium이며 실제 휴대폰 결과가 아니다. 결승에1000개를 모은 스트레스 결과를 대신하지도 않는다.

준비 Worker의1000개 생성·첫 응답은 약40~~43ms였다. 입력 변경 후 기다리는200ms는 제외했다. 경기 Canvas 한 번의 그리기는 평균0.44~~1.08ms, 미니맵은 평균0.20~~0.21ms였다.5초 동안 메인 스레드에서 표본으로 잡힌 비용은 상태 해석0.3~~8.3ms, 복사·보간4.6~~46.8ms, 순위 갱신15.1~~38.2ms였다. ON 조건의 음향 JavaScript 처리는1.0~3.8ms였다. 음향 엔진의 다른 실행 스레드 비용은 포함하지 않는다. 표본에서 분류하지 못한 비용도 크므로 이 수치를 전체 처리 비용으로 합산하지 않는다. 한 번의 짧은 측정에서 ON 출발이 더 빨랐다는 이유로 스킬이 성능을 높인다고 해석하지 않는다.

Worker 내부를 분리한 Node.js 진단에서는 같은 초기 배치로3경기초·360단계를 실행했다. 상태 포장은2단계마다180회 수행했다. 함수 계측 비용이 포함되므로 브라우저 수치와 직접 비교하지 않는다.

| 구간        | 물리 계산 전체 | 결승 위치 보정 | 상태 포장 | 포장 결과 복사 |
| ----------- | -------------: | -------------: | --------: | -------------: |

복사 수치는 `structuredClone` 호출이며 실제 Worker 전송 전체의 시간은 아니다. 브라우저의 Worker 요청부터 응답까지는 물리 계산·포장·전송·실행 대기를 함께 포함한다. 결승 밀집 ON의 평균 요청 응답 시간은421.9ms였다. 이 진단과 위치 보정 비용을 함께 보면 전송보다 물리 계산이 주된 지연 원인이다.

비교 사이트도 같은 Chromium·1280×720·구슬1000개·마지막 방식에서 측정했다. 구슬을 섞은 뒤 자연스럽게 진행시켜 출발·중간·후반을5초씩 기록했다. 소리·스킬 조건은 우리 기능과 같지 않으며, 결승에1000개를 모은 우리 스트레스 배치와도 다르다.

- 비교 사이트는 측정 창마다 약120fps와 약5경기초 진행을 유지했다. 중간에는987개, 후반에는912~919개가 남아 있었다.
- 물리 엔진의 한 단계 비용은 평균0.80~~1.26ms였다. 단계별95% 값은1.5~~2.3ms였다.
- 화면 그리기는 평균 약2.9~3.4ms였다. 우리 Canvas 그리기가 더 느리다는 근거는 이 측정에서 나오지 않았다.
- 준비 상태에서도 물리 단계 호출은 발생하지만 구슬이 활성화되지 않는다. 이를 실제 경기 진행으로 계산하지 않았다.

## 확인된 원인과 남은 추정

확인된 가장 큰 문제는1000개 결승 밀집의 접촉 계산이다. 이번 겹침 수정은 위치를 최대32회 다시 풀기 때문에 한 번만 분리하던 기존 방식보다 계산량이 늘었다. 정확도 개선이 대규모 밀집 성능까지 해결한 것은 아니다. 같은 시험에서 소리·스킬을 꺼도 느렸으므로 두 기능만 끄는 것으로 해결되지 않는다.

코드에서 확인한 추가 비용은 구슬 분리와 벽 검사, 응답마다 장치5596개의 변경 여부를 확인하는 순회다. 큰 맵과120Hz 내부 분할은 비교 사이트와 다른 작업량을 만든다. 다만 장치 수가 약122배라는 이유로 실행 시간도122배라고 계산할 수는 없다. 가까운 장치만 충돌 후보로 고르기 때문이다. 두 엔진을 같은 맵에서 비교하지 않았으므로 Box2D 자체의 이득도 아직 추정이다.

현재 화면·Worker는 긴 지연을 모두 따라잡지 않고 누적 시간을80ms로 제한한다. 보간 시간도 제한되어 다음 응답을 기다리는 동안 표시 위치가 머문다. 큰 지연에서 실제 경기가 느려지는 현상과 화면이 끊기는 현상에 각각 영향을 준다. 제한만 늘리면 더 큰 계산 묶음이 생겨 버튼 응답과 일시정지 처리가 나빠질 수 있다.

## 다음 개선 우선순위

1. 결승에서 연결된 접촉 목록과 공간 구획을 반복 사용하고, 이미 풀린 접촉 묶음의 재검사를 줄인다. 가장 큰 비용부터 줄일 수 있다. 계산 순서·겹침·벽 관통·고정 구슬·도착 순위가 달라지지 않는지 회귀 검사가 필요하다.
2. 물리 처리 여력이 확보되면 응답 주기와 표시 지연을 조정한다. 몇 개의 과거 상태를 모아 보간하면 수신 간격 변화에 덜 흔들릴 수 있다. 반응이 늦어지는 대가가 있으며 물리 계산 용량 부족 자체는 해결하지 못한다.
3. 변경된 장치만 상태로 보내고 표시용 배열을 재사용한다. 순회와 메모리 정리를 줄일 수 있다. 초기화·파괴·복원 상태를 빠뜨리지 않아야 한다.
4. 정지한 준비 화면과 미니맵은 바뀐 때만 그리는 방식을 검토한다. 전력·화면 처리 비용을 줄이지만 결승 물리 병목의 직접 해결책은 아니다.
5. 별도 시험에서 Box2D-WASM을 같은 맵·명단과 비교한다. 재질·스킬·고정·난수·결승 순서를 다시 맞춰야 하므로 엔진 교체는 큰 변경이다. 그리기 해상도 선택은 선명도를 낮추는 대가가 있으며 현재 측정의 우선 해결책은 아니다.

이 분석의 추가 일반 최적화와 엔진 교체는 이번 구현에 포함하지 않는다.1000개 결승 밀집을 실시간으로 처리한다는 완료 주장을 하지 않는다. 재현 스크립트·원시 측정·화면 캡처는 Git이 무시하는 로컬 `.context/`에 두었다.

## 검증

60개 밀집·회전 각도4가지에서 최대 겹침은0.84였고 모두18.53경기초 안에 완주했다. 양쪽 원호의 대칭·통로, 양쪽1열, 고정·도착 구슬,0.25·1·2배속의 같은 경기 시각을 검사했다. 위아래2개가 회전바에 튕기는 실제 상태와0.25배속의 중간 보간에서도 구슬·회전바 겹침1 이하와 완주를 확인했다. 기존 접전32조합도 확인했다. 원호형 접전 표본에서는 역전6회가 남았으며 직선형의10회보다 많다고 주장하지 않는다.

준비1000개의 번호·색·시작 위치 일치와 백만 개 준비 도중 취소를 검사했다. 접근성 snapshot을 먼저 확인하고 모바일·데스크톱의 번호 구슬·진행률·긴 이름·1000등 검색·선택·복사를 확인했다.4자리 번호가 구슬 안에 들어가고 진행률과 겹치지 않는 실제 화면도 확인했다.

- 구슬 레이스 단위178개 통과 후 위아래2개 보간 검사를 추가했다. 결승 관련6개를 다시 실행해 통과했으며 고유 검사 수는179개다.
- build 화면의 브라우저70개 중68개가 먼저 통과했다. 나머지2개는 번개·바람 추가 이전의 음원 예상 목록을 쓰고 있었다. 현재3종 스킬 목록으로 수정했다. 문구 수정도 반영한 최종 build에서 해당2개를 포함해 안내·미리보기·순위·카메라12개를 다시 실행했고 모두 통과했다.
- 정적 검사 오류·경고0개, 변경 파일 ESLint·Prettier, UI 검사, 정적 build 결과 검사, 변경 요구사항4개와 화면 연결 검사를 통과했다. `git diff --check`도 통과했다.
- 전체 요구사항 검사는 이번에 변경하지 않은 `REQ-MARBLE-005`의 `kind: behavior`를 현재 validator가 허용하지 않아 실패했다. 변경 요구사항만의 통과와 구분한다. 전체 프로젝트의 lint·단위·브라우저 검사는 실행하지 않았다.
- build는 예정한1회 후 마지막 안내 검수에서 찾은 조사 오류2곳을 반영하기 위해1회를 추가했다. 생성 결과를 직접 고치지 않고 source 수정 후 다시 build했다. 최종 build의 안내 문구와 관련 브라우저 검사를 확인했다.
