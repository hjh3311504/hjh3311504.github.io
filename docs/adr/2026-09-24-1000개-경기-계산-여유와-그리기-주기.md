# 1000개 경기 계산 여유와 그리기 주기

- 상태: 적용
- 날짜: 2026-09-24
- 연결 요구사항: REQ-MARBLE-002, REQ-MARBLE-004
- 연결 화면: [SCR-WEB-004](../design/screens/SCR-WEB-004.md)

## 문제와 확인

[결승 격자와 반복 보정 계산 축소](2026-09-24-결승-격자와-반복-보정-계산-축소.md) 뒤에도1000개·2배속의 심한 밀집에서 실제 진행 속도가 부족했다. 이전 build의105경기초부터 실제10초 측정은약1.725배속이었다. 화면은120fps였지만 경기 계산이 그 속도를 따라가지 못했다.

같은105경기초 저장 상태와 출발부터 실행한 브라우저 경기를 모두 사용했다. 일반 블록이나 구슬을 제거하지 않았다. 화면fps, 상태 수신 빈도, 실제 시간당 진행한 경기 시간을 구분했다. 한 구간의 평균뿐 아니라 그 뒤의 연속 구간과 처리하지 못한 남은 시간도 확인했다.

Node와 브라우저에서는 같은 난수로 시작해도 긴 경기의 미세한 수치 차이가 쌓일 수 있었다. Node 저장 상태의 계산 비용만으로 브라우저 성능을 판단하지 않았다. 브라우저에서 따로 재현한126~131경기초는 물리 한 단계가 평균약5.94ms였다.2배속에 필요한240단계/초의 평균 예산약4.17ms를 넘었다.

## 결정

### 밀집 접촉의 초기 보정

미도착 구슬이64개를 넘는 실제 위치 보정의 첫3회는 위아래로 쌓인 접촉을 먼저 분리한다. 두 구슬이 모두 움직일 수 있고, 높이 차가 반지름 합의 절반보다 큰 접촉만 대상이다. 가로 위치를 유지한 채 두 원이 겹치지 않는 데 필요한 세로 간격을 계산해 위쪽 구슬에 적용한다.

이미 아래쪽부터 정렬한 접촉을 사용하므로 아래 벽의 압력이 위쪽 이웃으로 작은 보정을 여러 번 거쳐 전달되는 비용을 줄인다. 근접한 가로 접촉과 움직일 수 없는 구슬의 접촉은 기존 양쪽 보정을 따른다. 이후 반복도 기존 양쪽 보정으로 진행한다. 각 반복에서 벽·회전바를 다시 보정하고, 탐색 범위를 벗어나면 이웃을 다시 찾는다. 최종 남은 겹침 확인을 통과해야 조기 종료한다.

이 초기 위치 보정은 속도를 추가하지 않는다. 구슬 반발계수0.8과 기본 충돌의 반발 속도, 연결 접촉의 닫히는 상대 속도 제거는 유지한다. 번개 구슬의 이동 가능 여부도 기존 회전바 압력 연결 판정을 따른다. 얼음 고정과 도착 구슬은 이동시키지 않는다. 표시 보정과64개 이하에는 위쪽 우선 분리를 적용하지 않는다.

기본1/120경기초, 내부 이동 분할, 지형, 회전바, 스킬, 종료 오차0.5·0.15와 최대512회를 유지한다. 큰 밀집 경기의 보정 경로·궤적·도착 시각은 이전 구현과 달라질 수 있다. 같은 구현에서 난수와 경기 시각이 같으면 배속별 결과는 같아야 한다.

### 중복 계산과 배열 접근 축소

- 기본 구슬 충돌 격자도 현재 높이 범위의 연속 정수 배열로 조회한다. 폭720에 맞춰 한 줄32칸을 사용하고 범위 밖으로 보정된 구슬은 임시 Map에 담는다. 이웃 연결과 번호순 충돌은 유지한다.
- 쌍 처리 중 위치가 바뀌지 않는 고정 구슬과 큰 경기의 결승 구슬은 닿지 않는 후보를 정렬 전에 제외한다. 후보는 구슬 번호로 정렬한다.
- 닿은 블록이1개면 충돌 순서 계산을 생략한다.2개 이상이면 기존10회 접촉 시점 탐색과 정렬을 그대로 수행한다.
- 직선 면의 거리는 한 축이0일 때 절댓값으로 계산한다. 이동 분할에 필요한 최대 속도는 제곱값의 최댓값을 모은 뒤 한 번만 제곱근을 구한다. 같은 내부 단계의 감속값을 재사용한다. 모든 구역 진입을 기록한 구슬의 구역 재확인도 생략한다.
- 결승 보정에서 벽 후보가 없고 탐색 여유 안에 있는 구슬은 결과가 그대로인 벽 투영을 생략한다. 벽·경기장 경계·큰 이동은 계속 확인한다.
- 다음 반복의 이전 위치를 현재 순회 끝에 기록해 별도 복사 순회를 줄인다. 쌍 계산에서도 읽은 좌표·속도를 재사용한다. 구슬 구성이 같으면 직전 물리 단계의 정렬 순서에서 시작해 같은 비교 기준으로 다시 정렬한다.
- 반복 보정의 좌표·속도·반지름은 빈칸 없는 숫자 배열로 재사용한다. 초기값은 실제 경기 상태로 덮어쓴다.

### 화면 주기

200개 이상은 화면 보간과 그리기를 최대60fps로 제한한다. 작은 경기는 화면의 원래 주기를 따른다. 건너뛴 화면 프레임을 나중에 몰아서 그리지 않는다. 카메라에는 마지막으로 그린 뒤 실제 지난 시간을 전달한다.

물리 Worker 요청과 남은 경기 시간은 화면 일정과 독립적으로 유지한다. 상태 수신, 스킬·효과음 이벤트의 누적과 소비도 유지한다. 화면fps는 실제2배속을 대신하는 지표가 아니다. 실제 경기 시간의 증가량으로 배속을 확인한다.

## 제외한 실험

- 화면60fps만 적용한 실제 경기에서105경기초 이후는약2.10배속이었지만 다음 구간은약1.77배속이었다. 뒤에서 밀린 시간을 따라잡으므로 첫 구간만으로2배속 유지라고 결론 내리지 않았다.
- 화면을30fps로 더 낮춰도약1.76배속 구간이 남았다.30fps 제한은 제외했다.
- 실제 보정 종료 기준0.8은 보관한 후기 상태에서 평균5.94ms를3.41ms로 줄였다. 그러나 출발부터 이어진 경기의85~100경기초에서약1.52배속 구간이 나타났다.0.9·0.95 실험은 겹침1 이하 검사에도 실패했다. 최종 기준은 기존0.5로 복원했다.
- 내부 이동 분할 축소, 보정량·관성·위치 가중치 변경, 이전 보정 추정, WebAssembly·동시 좌표 연산 등도 비교했다. 효과가 작거나 계산이 늘거나 안전 검사를 통과하지 못한 방식은 채택하지 않았다. 제품에 새 실행 환경이나 의존성을 추가하지 않았다.

## 검증 결과

### 계산 비용

원본105경기초 상태에서5경기초·600단계를 계산했다. 작업 시작 코드와 최종 코드를 번갈아3회 실행했다. 다른 경기나 검사를 동시에 실행하지 않았다.

| 측정                          | 작업 시작 코드 | 최종 코드 |
| ----------------------------- | -------------: | --------: |
| 물리 한 단계 평균,3회 평균    |        4.188ms |   1.873ms |
| 물리 한 단계95백분위,3회 평균 |        7.254ms |   2.581ms |
| 600단계 순수 계산,3회 평균    |        2.513초 |   1.124초 |

평균 계산 비용은약55.3% 감소했다. 각 구현의3회 결과 해시는 각각 같았다. 초기 위치 보정이 달라져 전후 구현의 궤적과 해시는 다르다.110경기초 도착 수도107개에서106개로 달라졌다. 초기 분리 도입 전의 순수 중복 계산 축소 단계에서는 이전 종료 기준0.5의 상태·이벤트 해시가 그대로 일치했다.

### 물리·상태·이벤트 검사

- 관련 단위 검사200개 중198개 통과, 기존 실패2개 유지. 기존 실패는 과거 결승 바180·290·320길이의 반전 횟수·높이 비교다. 작업 전 기록과 같은 수치로 실패했다. 이번 성능 작업에서 기준이나 회전바를 바꾸지 않았다.
- 1000개·스킬ON 밀집12경기초·회전각2가지: 최대 실제 겹침0.499998, 표시 겹침0.499920 미만. 매 단계 실제 상태와 표시 상태를 각각 확인했다.
- 1000개·회전각4가지·35경기초: 벽 반대편 이탈 없음. 도착 구슬은 중앙 통로를 통과했다.
- 60개 밀집·회전각4가지: 최대 실제 겹침약0.622.48.775~55.375경기초에 전원 도착했다.
- 원본105경기초 저장 상태를 최종 코드로5경기초 계산: 최대 실제 겹침0.499951, 표시 겹침0.498429 미만. 벽·중앙 골인·표시 보정의 실제 상태 불변 검사 통과. 벽438개·고무547개·스킬16개·회전바32개의 이벤트를 확인했다.
- 1000개 경기의 번개 고정3개 연결 밀림, 정지 시각·속도 유지, 얼음 고정 예외 제외 검사 통과.0.25·1·2배속의 같은 경기 시각 결과 일치 검사도 통과했다.
- Svelte 정적 검사 오류0개·경고0개. 변경 코드 ESLint·Prettier·UI 검사, REQ-MARBLE-002 화면 연결과 전체 문서 연결, 정적 build 검증 통과. REQ-MARBLE-004는 구조 요구사항이므로 UI 요구사항 전용 선택자로 검사하지 않았다.
- 최종 화면용 build는1회만 수행했다. 전체 lint와 다른 도구의 전체 단위 검사는 실행하지 않았다.

### 최종 build 브라우저 검증

`test:e2e:built`로 관련 Playwright11개가 통과했다.1440px·1000개와390px·100개에서 화면을10fps로 낮춰도 계산이2배속으로 진행했고, 일시정지·재개·초기화가 정상 동작했다.1440px·390px의 번개·바람 발동, 회전바 되튕김·번개 고정의 표시 위치, 당첨 효과 정리도 통과했다.

1440×1000 데스크톱 브라우저에서 도각도각 키보드·1000개·난수47·마지막·스킬/소리ON·2배속으로 출발부터 실행했다. 접근성 snapshot으로 설정과 시작 상태를 먼저 확인했다. 측정 중 다른 경기·검사·build는 실행하지 않았다.

출발 실제10초는1.9934배속이었다.85경기초부터는 실제10초씩5개 구간을 연속 측정했다. 실제 시간은 `performance.now()`, 경기 시간은 Worker 상태의 `time`, 화면 그리기는 Canvas 전체 배경을 그린 횟수로 각각 측정했다.

| 경기 구간           | 실제 진행 속도 | 구간 내 최대 결승 밀집 |  상태 수신 | Canvas 그리기 |
| ------------------- | -------------: | ---------------------: | ---------: | ------------: |
| 85.06~105.05경기초  |     1.9989배속 |                  351개 | 51.99회/초 |      59.99fps |
| 105.05~125.05경기초 |     1.9999배속 |                  350개 | 52.10회/초 |      60.00fps |
| 125.05~145.05경기초 |     1.9992배속 |                  356개 | 52.18회/초 |      59.98fps |
| 145.05~165.07경기초 |     2.0014배속 |                  358개 | 52.59회/초 |      59.99fps |
| 165.07~185.08경기초 |     2.0016배속 |                  353개 | 52.00회/초 |      60.00fps |

사용자가 제공한105경기초 이후약1.41배속과 이번 작업 시작 build의약1.725배속에서, 최종 build는 같은 시각 구간에약2.000배속으로 개선됐다. 최대358개가 밀집한 구간을 포함해5개 연속 구간 모두약1.999~2.002배속을 유지했다. 이 결과는 화면fps 증가로 대신한 수치가 아니다.

각 구간의 처리하지 못한 실제 시간은 최대4.167ms, 구간 끝은0.767~~2.000ms였다. 미뤄 둔 시간이 계속 쌓였다가 다음 구간에서 따라잡는 현상은 없었다. 구간 내 Worker 요청 간격 최댓값은9.2~~10.3ms였다. 기존 실제 시간 입력 상한80ms에 닿지 않았고, 시간을 버리는 새 처리를 추가하지 않았다.

화면 검증은1440×1000과390×844에서 접근성 snapshot을 먼저 확인했다. 결승·중앙 통로·회전바와 조작부를 직접 확인했다. 두 화면 모두 가로 넘침이 없었다. 데스크톱 정지 응답은약30ms였으며,185.225경기초에 받은 실제 상태의 결승 겹침 최댓값은약0.292였다. 화면 자료는 `output/playwright/perf-2x-final/desktop.png`, `mobile.png`다.

## 남은 한계

- 이 성능 결과는 현재 데스크톱 환경의 지정한 설정과85~185경기초 구간에 대한 측정이다. 다른 기기·브라우저·난수·더 큰 밀집에서도 항상2배속이라고 보장하지 않는다. 모바일은 같은 데스크톱 브라우저의 화면 폭 검증이며 모바일 실기 성능 측정이 아니다.
- 같은 구현의 배속별 재현성은 유지했지만, 초기 위치 보정이 바뀐 큰 경기는 이전 구현과 궤적·도착 순서가 달라질 수 있다.
- 최대512회 이후에도 모든 가능한 배치의 겹침을 수학적으로 보장하는 것은 아니다. 이번1000개 스트레스·실제 저장 상태에서 실제·표시 겹침1 이하와 벽 통과 방지를 확인했다.
- 과거 회전바 길이 비교 단위 검사2개는 여전히 실패한다. 기존 실패를 이번 변경의 통과로 처리하지 않는다.
