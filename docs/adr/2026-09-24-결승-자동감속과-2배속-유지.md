# 결승 자동 감속과 선택한2배속 유지

- 상태: 적용
- 날짜: 2026-09-24
- 연결 요구사항: REQ-MARBLE-003, REQ-MARBLE-004
- 연결 화면: [SCR-WEB-004](../design/screens/SCR-WEB-004.md)

## 요청과 재현

사용자는1000개·2배속 경기에서 결승에 도달하면 렉처럼 갑자기 느려진다고 보고했다. 현재 배치인 회전축 x160·결승 시작점+480, 길이440, 경사40°/30°로 다시 조사했다. 조사 중 사용한 당첨 방식과 느려질 때의 배속 표시를 질문했지만, 이 기록 시점에는 추가 답변을 받지 못했다. 따라서 아래 재현이 사용자가 겪은 모든 감속의 원인이라고 단정하지 않는다.

### 마지막 방식

최종 build를1440×1000·키보드·난수47·1000개·마지막·스킬/소리ON·2배속으로 실행했다.50경기초부터 미니맵으로 결승을 직접 보고170경기초까지 실제10초씩6구간을 측정했다.

- 실제 진행 속도: 1.9962~2.0023배속.
- Canvas 그리기: 약60fps. 상태 수신: 약52회/초.
- 최대 결승 밀집: 314개.
- 화면 갱신 콜백의95백분위 비용: 약1.0~1.1ms.120Hz 브라우저에서 건너뛴 화면 콜백도 포함한다.
- Worker 요청 왕복 평균: 약1.61~1.96ms. 이 수치는 순수 물리 계산만의 시간이 아니다.

이 조건에서는 보고된 지속 감속을 재현하지 못했다. Node에서도 난수1/7/17/47/2026 각각120경기초를 계산해5경기초 단위로 비용을 기록했다. 평균 한 단계는약1.48~2.72ms 범위였으며 가장 느린 구간은 결승 전이었다. 이 추가 측정은 사용자의 기기 성능을 보장하지 않는다.

### 첫번째 방식

같은 설정에서 당첨 방식만 첫번째로 바꾸면약31.77경기초에 갑작스러운 감속이 재현됐다. 화면은약60fps였지만 실제 진행 속도는약0.25배속이었다. 버튼도0.25배속으로 바뀌고 잠겼다. 당첨 직후 선택한2배속으로 돌아왔다.

`race-worker.js`는 결승 연출의 `cinematic.active`가 켜지면 사용자가 고른 배속과 관계없이0.25를 사용했다. 페이지의 계산 요청 간격과 배속 표시도 같은 강제 감속을 따랐다. 따라서 이 재현은 화면 렉이나 밀린 계산 때문에 발생한 것이 아니다.2배속과 비교하면 실제 경기 진행이8분의1로 느려지는 기존 연출이었다.

## 조치

사용자의2배속 경기 감속 조사·조치 요청에 따라, 명시적으로 선택한2배속을 결승 연출에서도 유지한다.1배속 경기의 기존0.25배속 연출은 유지한다. 카메라 확대·후보 추적·당첨·팡파레·연출 중 배속 전환 잠금은 유지한다.

`effectiveRaceSpeed()`를 Worker의 시간 소비, 페이지의 다음 요청 간격, 버튼과 화면 읽기 안내에서 함께 사용한다. 화면에2배속만 표시하고 실제 계산은 느리게 진행하는 불일치를 막는다. FAQ와 현재 요구사항도 같은 규칙으로 갱신한다.

과거 ADR의 자동 감속 설명은 보존하고, 선택한2배속의 예외를 이 문서에 기록한다. 물리 간격1/120경기초, 겹침 보정, 벽 통과 방지, 회전바·지형·반발·스킬 규칙은 변경하지 않는다. 경기 시간을 버리는 처리도 추가하지 않는다.

## 검증 범위

- 선택한2배속의 결승 시작·후보 변경·당첨 전후 배속을 검사한다.1배속의 자동 슬로모션과 원래 배속 복귀도 검사한다.
- 실제 Worker의2배속 경기에서 연출 중에도 요청 시간의2배만큼 진행하는지 확인한다. 같은 물리 단계의 직접 계산과 위치·당첨 이벤트를 비교한다. 이 검사는 수정 전 강제 감속 코드에서 실패한다.
- 기존 Worker 통합 검사는 요청당 최대4단계와60Hz 상태 묶음을 반영하도록 요청을1단계 단위로 보내고 상태를 즉시 받게 갱신했다. 요청의 남은 시간을 무시하고19단계를 기대하던 방식으로 검사하지 않는다.
- 카메라·당첨 범위·마지막 당첨·Worker 단위37개가 통과했다. 관련 스킬·배속 재현성·상태 묶음·화면 주기 검사도 별도로 실행했다.
- 물리 함수는 변경하지 않았다. 기존 과거 반동 비교 실패2개와 다른 도구의 전체 검사는 이번에 다시 실행하지 않았다.

## 최종 build 검증

- 관련 단위 검사65개(기본37개·추가28개), Playwright8개가 통과했다.1배속의 기존 슬로모션·카메라,2배속 유지, 당첨 범위·팡파레1회·마지막 실제 골인, 정지·재개·초기화를 확인했다.
- Svelte 정적 검사 오류0개·경고0개, 변경 코드 ESLint·Prettier·UI 검사, REQ-MARBLE-003·전체 화면 연결, 정적 build 검사가 통과했다. 최종 화면 build는1회 수행했다. 전체 lint와 다른 도구의 전체 테스트는 실행하지 않았다.
- 같은1000개·첫번째·난수47·스킬/소리ON·2배속 경기를 최종 build에서 실행했다. 결승 연출 시작의 접근성 snapshot에서 버튼과 Canvas 안내가2배속을 표시하는지 확인했다. 수정 전에는 같은 순간0.25배속을 표시했다.

| 구간                             | 수정 전                          | 수정 후                     |
| -------------------------------- | -------------------------------- | --------------------------- |
| 결승 연출 진입 직후 실제 진행    | 약0.25배속                       | 약2.00배속                  |
| 같은 구간의 Canvas 그리기        | 약60fps                          | 약60fps                     |
| 밀집50~110경기초·실제10초씩3구간 | 별도 마지막 방식 측정에서약2배속 | 2.00071/1.99980/1.99922배속 |

수정 후 결승 진입 직후6개1초 측정의 평균 진행 속도는약2.00배속이었다. 개별1초 값은 상태 수신 경계에 따라1.959~2.032배속이었다. 밀집 구간에는 최대314개가 결승에 있었고, 처리하지 못한 시간은 최대4.17ms로 계속 늘어나지 않았다. Canvas의약60fps와 실제 경기 시간의 진행을 별도로 확인했다.

이번 수정은 강제 슬로모션의 동작을 바꾼 것이다. 물리 한 단계를 더 빨리 계산하는 최적화라고 보고하지 않는다.2배속 표시를 유지하면서 실제 진행이 느려지는 다른 기기·브라우저의 현상은 이번 환경에서 재현하지 못했다. 해당 현상이 이어지면 사용한 당첨 방식·브라우저·맵·느려지는 경기 시각을 추가로 확인해야 한다.

접근성 snapshot을 먼저 확인한 뒤1440×1000·390×844 준비 화면과 실제 결승 화면을 확인했다. 배속 표시·버튼·당첨 패널에 잘림이나 가로 넘침은 없었다. 브라우저 console 오류·경고는0개였다. 화면 자료는 `output/playwright/perf-followup/final/`에 남겼다.

## 재현 자료

`.context/perf-followup/`에 `baseline.log`(마지막 방식), `first-baseline.log`(첫번째 자동 감속), `seeds.log`(다른 난수 계산 비용), `unit.log`, `timing-safety.log`, `regression-before.log`, `final-speed.log`, `e2e.log`를 남겼다. 브라우저 측정은 Playwright CLI로 실행했다. 접근성 snapshot으로 상태와 배속 표시를 먼저 확인했다.
