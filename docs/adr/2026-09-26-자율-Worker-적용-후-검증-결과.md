## 로컬 검증

최종 build1개를 재사용했다. 구슬 레이스 브라우저84개와 별도 계측4개가 통과했다. 내부 시계·Worker·전송·계측 단위17개, 정적 검사, 변경 코드 lint·포맷, UI 규칙, workflow 문법, 정적 build 결과 검증도 통과했다. 다른 도구의 전체 단위·브라우저 검사는 로컬에서 반복하지 않았다.

실제 경기의 결승은1000개·도각도각 키보드·난수47·마지막·스킬과 소리ON·2배속으로 출발부터 계산했다.105경기초부터 실제10초씩2회 측정했다. 강제0.25배속 연출이 없는 구간이었다. 구슬 고정이나 블록 삭제는 하지 않았다.

| 조건                              | 실제 배속 | Canvas fps | 상태 수신/초 | 표본 끝 결승 구슬 |
| --------------------------------- | --------- | ---------- | ------------ | ----------------- |
| 데스크톱1440×1000·첫 구간         | 2.000배   | 59.99      | 52.29        | 264개             |
| 데스크톱·다음 구간                | 2.001배   | 60.00      | 51.80        | 292개             |

| 모바일·다음 구간                  | 1.996배   | 54.18      | 49.30        | 289개             |

로컬 Apple M5·Chromium151의 결과다. 모바일은 실제 휴대폰이 아닌 화면 크기와 CPU 감속 조건이다. 직전 코드도 이 로컬 결승 조건에서 약2배속을 유지했으므로 로컬 결과만으로 변경의 개선율을 계산하지 않는다. 물리 코드는 바꾸지 않았으며 이전 같은 물리 코드의 실제·표시 겹침0.5 미만,1000개·회전각4가지 벽 통과 방지, 중앙 골인, 배속 재현성 기록을 유지한다. 이번 브라우저84개에는 번개 고정 중 바에 밀리는 화면, 필수0.25배속, 효과음·스킬, 정지·재개·초기화, 종료 후 설정 변경 검사가 포함됐다.

계측을 추가한 별도 출발·진행2배속 표본에서 데스크톱 물리1단계 평균은0.93~~1.31ms, 모바일 CPU4배 감속은1.07~~1.22ms였다. 모바일 응답 전달은 평균4.21~10.96ms였지만 계산은 이 시간을 기다리지 않았다. 계측 비용이 포함된 숫자이므로 일반 검사와 합치지 않는다. 원본은 `.context/autonomous-worker/final-e2e.log`, `final-profile.log`, `finale-live.log`다.

## 원격 검증

[실행36238877068](https://github.com/hjh3311504/hjh3311504.github.io/actions/runs/36238877068)은 실패했다. AMD EPYC7763·4CPU·약16GB·Chromium151에서 같은 build로 요청 방식과 자율 방식을 차례로 비교했다. 기준 방식4개 중1개 통과·3개 실패, 현재 우선 검사7개 중4개 통과·3개 실패였다. 기준 단계의 `continue-on-error` 때문에 GitHub 단계 결론은 success로 보이지만 기준 검사 통과를 뜻하지 않는다. 실제 보고서의 실패를 확인했다.

| 2배속 조건         | 구간 | 이전 요청 방식 | 자율 Worker   | 현재 Canvas fps |
| ------------------ | ---- | -------------- | ------------- | --------------- |
| 데스크톱           | 출발 | 1.607배        | 1.863~1.886배 | 40.7~41.7       |
| 데스크톱           | 진행 | 1.272배        | 1.471~1.528배 | 51.2~52.1       |
| 모바일·CPU4배 감속 | 출발 | 1.537배        | 2.046~2.071배 | 17.5~19.2       |
| 모바일·CPU4배 감속 | 진행 | 1.434배        | 2.024~2.079배 | 21.3~22.6       |

기준은 각1회, 현재는 실패에 따른 최초 실행과재시도2회다. 진행 구간의 실제 배속은 데스크톱 약16~~20%, 모바일 약41~~45% 높아졌다. 서로 경기 시간이 달라 이후 지형의 접촉 상태까지 동일한 물리 미세 비교는 아니다. 필수0.25배속이 아닌 구간인지 확인했다.

500ms 동안 화면이 멈춘 뒤 실제2배속으로 따라잡는 검사와10fps 화면의 계산·정지·재개·초기화2개는 통과했다. 모바일2배속은 실제 속도 범위는 만족했지만30fps에 미달했고 재시도1회의 출발 잔여 시간도0.140초로0.1초 기준을 넘었다. 모바일1배속도14.1~~20.6fps로 실패했다. 데스크톱2배속은 물리 계산이 밀려 진행 구간 끝에 실제 시간1.48~~1.75초가 남았다. 이 시간을 버리지는 않았다.

원격 lint·UI 규칙·정적 검사·전체 단위 테스트·build는 통과했다. 뒤의146개 브라우저 검사와 정적 결과 검증은 실행되지 않았다. 별도 계측4개도1개 통과·3개 실패였다. 전체 PR이 통과했다고 표현하지 않는다.

## 남은 비용과 다음 작업

계측을 넣은 원격2배속 표본에서 데스크톱 물리1단계는 출발4.01ms·진행4.96ms였다.2배속에는1단계당4.17ms보다 충분히 짧아야 하므로 진행 구간의 계산 자체를 더 줄여야 한다. 같은 물리 단계와 접촉 순서를 유지하면서 일반 장애물의 구슬 쌍 분리·반복 블록 탐색을 줄이는 것이 다음 작업이다.

모바일 물리1단계는3.37~3.43ms였고 실제2배속을 유지했다. Canvas 함수는 평균10.42ms·8.30ms, 화면 콜백 전체는12.07ms·9.58ms였다. 응답 전달은42.98ms·29.92ms였지만 Worker 계산을 막지 않았다. 이 JavaScript 함수 시간만으로 낮은fps 전체를 설명할 수는 없으므로 다음에는 브라우저 trace에서 그림 변환·화면 합성과 메인 스레드 예약 시간을 나눠 확인해야 한다. 화면 해상도·표시 규칙·성능 기준을 낮추는 변경은 적용하지 않았다.

원본은 `.context/autonomous-worker/remote.log`와 원격의 `marble-request-driven-baseline`, `marble-performance`, `marble-diagnostics` 보고서다. 로컬 결승2배속 유지는 확인했지만 원격 데스크톱2배속과 모바일30fps 목표는 아직 미달이다. PR merge·배포는 하지 않았다.
