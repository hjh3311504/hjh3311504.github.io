# PR 검사 시간을 줄인다

- 날짜: 2026-11-05
- 상태: 채택
- 범위: PR workflow, 브라우저 검사 배치, 경기 종료 검사 4개의 진행 속도. 제품 코드는 변경하지 않는다.
- 이전 결정: [PR 브라우저 검사 분산](2026-09-27-PR-브라우저-검사-분산.md)의 1번(build 1회 공유), 2번(`checks`의 전체 단위 테스트), 4번(환경 4개·worker 1개)과 "경기 시간을 줄이지 않는다"를 이 문서가 대체한다. 나머지 결정은 유지한다.

## 원인

사용자가 PR 검사가 너무 길다고 지적했다. PR #82 실행 [41975981116](https://github.com/hjh3311504/hjh3311504.github.io/actions/runs/41975981116)은 약 7분(416초)이 걸렸다.

- 가장 늦은 흐름은 `site-build` 53초 → 브라우저 4번 묶음 354초였다. 브라우저 job은 `site-build`가 끝나야 시작했다.
- 묶음별 테스트 실행 시간이 168·217·208·300초로 고르지 않았다. 배치 표가 오래됐고 `bracket`·`aram-mayhem`·`analytics`·`wheel-audio`·`app-update` 파일이 표에 없었다.
- 각 묶음은 worker 1개로 테스트를 하나씩 실행했다. runner는 CPU 4개다.
- 경기 종료를 기다리는 `marble-race.spec.js` 검사 4개가 1배속으로 각각 46~59초 걸렸다.
- `checks`의 단위 테스트는 109~191초였고 대부분 구슬 레이스 물리 테스트였다. 브라우저 흐름이 짧아지면 이 job이 가장 늦어진다.

## 결정

1. 배치 표를 PR #82 실측 시간으로 갱신하고 모든 일반 검사 파일을 넣는다. 표에 없는 파일이 생기면 `plan_browser_shards.js`가 경고를 출력한다.
2. 경기 종료 검사 4개는 출발 직후 2배속으로 바꾼다. 확인 대상은 결과 처리(당첨자 수, 도착 순위, 결과 복사)이며 기대값과 대기 제한은 유지한다. 1배속 실제 경기는 성능 job의 1000개 경기 검사가, 0.25·1·2배속의 결과 일치는 구슬 레이스 단위 테스트가 계속 확인한다.
3. 일반 브라우저 검사를 6개 환경에 나누고, 환경마다 `--workers=2`로 실행한다. `fullyParallel: false`를 유지하므로 같은 파일의 검사는 한 worker에서 순서대로 실행한다. 분할 수는 스크립트의 `shardCount`와 workflow matrix가 같아야 하며 `tests/ci`가 검사한다.
4. 브라우저·성능 job은 `site-build`를 기다리지 않고 같은 commit과 같은 PR 설정(가짜 수집 토큰·예약 도메인)으로 직접 build한다. `site-build`는 build 결과 검증과 `main` 배포 파일 생성을 맡는다. PR artifact `pr-site`는 더 만들지 않는다.
5. 단위 테스트를 `test:logic`과 `test:marble-race`로 나눈다. `checks`는 `test:logic`을, 새 `marble-logic` job은 구슬 레이스 물리 테스트를 실행한다. 로컬 `npm test`는 둘 다 실행한다. 최종 검사 `build`는 `marble-logic` 성공도 요구한다.
6. 성능·시간 보존 job(`marble-performance`)은 측정값이 흔들리지 않도록 worker 1개를 유지한다.
7. Playwright는 `--only-shell`로 headless 전용 Chromium만 설치한다. 검사는 모두 headless로 실행한다.

브라우저 설치 캐시는 넣지 않았다. 다운로드가 약 10초이고 캐시 복원에도 시간이 들어 효과가 작다.

- 마지막 실행에서 브라우저 묶음 6개의 테스트 실행은 84~~106초였다. 직접 build는 24~~42초 걸렸다.
- 경기 종료 검사 4개는 1개당 46~~59초에서 32~~47초로 줄었다.
- 4번 실행 모두 일반 브라우저 검사 235개와 성능 검사 12개가 통과했다. 재시도로 통과한 검사는 없었다.
- CPU를 나눠 쓰면서 개별 테스트 시간 합계는 약 20% 늘었다. 동시 실행으로 묶음 시간은 줄었다.
- runner 속도에 따라 같은 단계가 실행마다 15~20초씩 달라진다.

## 한계

- worker 2개는 소리·애니메이션 타이밍 검사의 안정성에 영향을 줄 수 있다. 재시도로 통과하는 검사가 반복되면 해당 파일을 worker 1개 job으로 옮긴다.
- 브라우저 검사가 쓰는 build와 `site-build`가 검증한 build는 같은 commit에서 따로 만든 파일이다. build 시각에 따라 달라지는 예약 글 공개 판정이 자정 무렵에 엇갈릴 수 있다.
- 실행 자원 사용량은 늘었다. build가 PR마다 1회에서 8회(`site-build`, 브라우저 6개, 성능 1개)로 늘고 job도 2개 늘었다.
- `marble-logic`은 약 3분이 하한이다. `physics.test.js`의 30경기 기록 검사 3개가 한 파일에서 순서대로 실행되고, 뒤의 검사가 그 기록을 함께 쓰기 때문이다.
- 한 파일은 한 worker에서만 실행되므로 `marble-race.spec.js`·`team-maker.spec.js`처럼 긴 파일이 묶음 시간의 하한이 된다.
- 배치 표가 오래되면 균형이 다시 나빠질 수 있다. 검사 누락이나 조건 완화로 이어지지는 않는다.
