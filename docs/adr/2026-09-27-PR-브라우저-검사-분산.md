# PR 브라우저 검사를 실행 시간에 따라 분산한다

- 날짜: 2026-09-27
- 상태: 채택
- 범위: PR workflow와 검사 배치. 제품 코드와 검사 조건은 변경하지 않는다.

## 원인과 기준 측정

사용자가 PR의 build 대기가 너무 길다고 지적했다. 직전 성공 실행[36246906247](https://github.com/hjh3311504/hjh3311504.github.io/actions/runs/36246906247)의 단계 시간을 확인했다.

| 단계                        | 소요 시간 |
| --------------------------- | --------: |
| 전체 build 작업             |  16분32초 |
| 실제 정적 build             |      11초 |
| 단위 테스트                 |   2분10초 |
| Chromium 설치               |      23초 |
| 비교용 요청 방식 성능 검사  |      48초 |
| 제품 성능·시간 보존 검사8개 |    1분8초 |
| 일반 브라우저 검사150개     |  11분23초 |

일반 브라우저 검사가 전체 시간의약69%를 차지했다. `marble-race.spec.js` 하나에약4분53초가 모였다. 특히 당첨 방식4종의 실제 경기 종료를 기다리는 검사는 각각약46~66초가 걸렸다. 테스트 개수나 파일 수만 똑같이 나누면 긴 검사가 한 환경에 몰린다.

## 결정

1. `site-build`가 정적 build와 결과 검증을1회 수행한다. PR에서는 같은 실행의 `pr-site` artifact를 모든 브라우저 작업에 전달한다. `main`에서는 기존 Pages artifact를 만든다.
2. `checks`가 lint·UI 규칙·정적 검사·전체 단위 테스트와 배치 로직 테스트를 실행한다. build·브라우저 작업과 별도 환경에서 진행한다.
3. 성능·시간 보존 검사는 전용 환경에서 기존 순서로 실행한다. 비교용 요청 방식과 실패 시 계측·추적도 유지한다.
4. 일반 브라우저 검사를 별도 환경4개에 배치한다. 각 환경의 Playwright worker는 기존1개다. 한 환경의 여러 경기가 CPU를 다투지 않는다.
5. `scripts/plan_browser_shards.js`가 Playwright에서 현재 전체 일반 검사 목록을 읽는다. 직전 측정 시간으로 오래 걸리는 묶음부터 가장 짧은 환경에 배치한다. 알려지지 않은 새 파일도 검사당5초의 배치 추정값으로 자동 포함한다.
6. 파일 안의 검사 순서와 공유 준비 작업은 유지한다. 예외는 `marble-race.spec.js`의 당첨 방식4개다. 이 검사는 각자 새 page에서 시작하고, `beforeEach`·`afterEach`가 page별 오류만 기록하며 공유 경기 상태가 없다. 각 검사를 독립적인 배치 단위로 취급한다.
7. 생성한 각 목록을 Playwright로 다시 읽어 계획한 검사 ID와 대조한다. 전체 목록의 누락·중복도 실패로 처리한다. 같은 줄에서 생성한 당첨 방식 검사는 전체 제목으로 구분한다.
8. 기존 최종 검사 이름 `build`를 유지한다. 의존 작업이 실패·취소되거나 PR에서 예상 밖으로 생략되면 성공으로 처리하지 않는다. `main`의 의도적인 PR 검사 생략은 허용한다. 배포는 `main`에서 이 최종 검사가 성공했을 때만 수행한다.
9. 일반 검사 보고서를 `browser-1`~`browser-4`에 각각 보존한다. 한 묶음이 실패해도 나머지는 끝까지 실행한다.

경기 시간을 줄이거나 저장 상태로 대체하지 않았다. 테스트 기대값·대기 제한·재시도·화면 녹화·실패 추적도 유지했다.

## 로컬 확인

- actionlint1.7.12: workflow 문법·표현식 검사 통과.
- 배치 단위 테스트3개 통과: 새 파일·여러 project 포함, 긴 경기 분산, 중첩 제목·같은 줄의 검사 구분.
- 실제 Playwright 목록150개 대조: 중복·누락0개.
- 묶음별 검사 수: 44·50·25·31개.
- 이전 실행 기록으로 추정한 묶음별 시간: 170.1·169.7·169.3·170.0초. 실행 환경 준비·업로드·대기 시간은 포함하지 않은 추정값이다.
- workflow의 build1회·분할 수·합산 의존 관계 확인. PR·push·수동 실행과 성공·실패·취소·생략 조합768개에서 합산 shell 조건 통과.
- 로컬 build1회와 정적 결과 검증 통과.
- 변경 JavaScript ESLint, 변경 파일 Prettier, `git diff --check` 확인.
- 전체 경기 테스트는 로컬에서 반복하지 않는다. 원격 PR에서 분산 실행 결과와 실제 시간을 확인한다.

## 한계

환경4개가 동시에 배정되어야 대기 시간이 줄어든다. GitHub 실행 대기열이나 환경별 CPU 편차에 따라 실제 시간은 달라진다. 환경별 설치 작업이 늘어 총 실행 자원 사용량은 증가할 수 있다. 배치 추정값이 오래되면 균형이 나빠질 수 있지만 검사 누락이나 조건 완화로 이어지지는 않는다.
