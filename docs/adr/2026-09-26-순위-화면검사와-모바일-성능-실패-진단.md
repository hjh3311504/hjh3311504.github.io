# 순위 화면 검사와 모바일 성능 실패 진단

## 실패 위치

PR33의 `a4451c4` 실행36225604053을 확인했다. lint·정적 검사·전체 단위 검사·사이트 build는 통과했다. 브라우저 검사149개 중146개가 통과했고 아래3개가 실패했다.

- 1000개 순위 검색·열 변경·추적:30초 초과.
- 추적 카드 고정·검색·교체·해제:30초 초과.
- 실제1000개·모바일 크기·CPU4배 감속:3차례 모두12.43~12.70fps로30fps 기준 미달.

이 실패로 정적 결과 확인과 배포 단계는 실행되지 않았다. 작업 이름이 `build`여도 실제 실패 단계는 `Test site in browser`다.

## 순위 검사 원인과 수정

`screenRace` 대역은 실제 물리를 진행하지 않고1000개의 높이를 모두 `finish.y - 100`으로 바꿨다. 좁은 결승 통로에1000개를 강제로 겹친 상태가 만들어져 화면 보간의 접촉 보정이 많은 계산을 수행했다. 이 상태의 표시 보정은 로컬 Node 표본5회에서 평균704.34ms였다. 결승 전의 겹치지 않는 배열은0.10ms였다. 실제 경기의 물리 성능 개선 수치가 아니라 잘못 만든 화면 검사 입력의 비용 비교다.

순위 검사2개에만 `ranking` 옵션을 적용한다. 결승 전 위치에26열·가로26·세로28간격으로 놓고 열마다 높이0.01차이를 둬 번호순 순위를 유지한다. 실제 경기·결승 반동·작은 구슬 겹침 화면 검사에는 이 옵션을 적용하지 않는다. 검색·스크롤·키보드·추적 고정·순위 교체·결과 복사는 계속 검사한다.

키보드 검사에는 다른 불안정 요소도 있었다. `cards.last().focus()`가 스크롤과 표시 목록을 바꾸면 다음 `cards.last().press()`는 다른 구슬을 누를 수 있었다. 실제로1000번 대신995번이 선택됐다. 두 동작 모두1000번 구슬의 접근성 이름으로 찾도록 바꾼다.

최초 재현에서는 순위 검사2개가22.2초·12.9초였다. 수정 뒤에는1.1초·1.4초로 통과했다.30초 제한과 기존 결과 확인은 유지한다.

## 화면 중복 계산

Canvas의 글자 크기·색은 같은 구슬 이름표 사이에서도 매번 지정하고 다시 읽고 있었다. 이름표의 일반·추적 스타일을 프레임마다 한 번 만들고, 글자 그림을 처음 만드는 때에만 Canvas 글꼴을 설정한다. 번호·이름·배경·그림 순서·좌표는 유지한다.

순위 아이콘은 글꼴이 이미 로딩된 경우에도 즉시 그린 뒤 `fonts.ready`에서 다시 그렸다. 글꼴 로딩 중에만 두 번째 그리기를 예약한다.

물리·경기 시간·배속·회전바·지형·스킬·효과음 규칙은 바꾸지 않는다. 프레임을 그렸다고 허위 집계하거나 표시 보정을 생략하지 않는다.

## 모바일 성능 조사와 남은 한계

로컬 CPU4배 감속의 기존 제품은 출발40.55fps·진행59.50fps로 통과했다. 따라서 GitHub의 CPU4배 결과를 같은 감속 배수만으로 로컬과 같다고 볼 수 없다.

로컬 CPU12배 진단에서는 원본이11.58/10.73fps, 화면 중복 계산 수정 뒤12.58/11.38fps였다. 한 번씩의 진단 표본이며 개선 폭을 보장하지 않는다. GitHub의4배 감속과 동일한 환경을 재현한 것도 아니다. 이 강한 감속 조건에서 실제 진행도 약0.38~0.42배속으로 느려졌다.

추가 실험은 임시 파일에서만 진행했다.

- 녹화·trace를 끈 경우12.38/11.23fps로 큰 변화가 없었다.
- Worker 요청을 중단해 같은 상태만 그려도 약14.74fps였다. 실제 진행은0이며 성능 개선안으로 채택하지 않는다.
- ImageBitmap 전환과 불투명 Canvas도30fps에 도달하지 못했다.
- 새로운 Chromium headless 모드는19.02/23.43fps였다. 실행 브라우저를 바꿔 통과시키지 않으며 기존 설정을 유지한다. [Playwright 공식 설명](https://playwright.dev/docs/browsers#chromium-new-headless-mode)에 따르면 기본 headless shell과 Chromium의 새 headless 모드는 다른 실행 방식이다.

Canvas 그리기 비용이 강한 감속 조건에서 크게 작용한다. 이번의 작은 중복 제거만으로 GitHub의30fps 실패가 해결됐다고 주장하지 않는다. 검사30fps·조작200ms·1000개·CPU4배 조건은 유지한다. 성능 표본은 실패 판단 전에 콘솔과 첨부 자료에 기록한다. 화면fps와 실제 경기 배속을 따로 기록해 다음 GitHub 실행에서도 진행 속도를 확인할 수 있게 한다.
